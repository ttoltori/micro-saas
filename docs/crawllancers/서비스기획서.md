# CrawlLancers 서비스 기획서

> 일본 Lancers의 공개 IT·시스템 개발 의뢰를 구조화하여 고객 니즈와 1인 개발자의 제품 기회를 발견하는 개인용 리서치 서비스

- 문서 버전: v1.0
- 작성일: 2026-08-02
- 프로젝트 코드: `crawllancers`
- 초기 운영 형태: 비공개 개인용 웹서비스

---

## 1. 서비스 개요

### 1.1 서비스 정의

CrawlLancers는 일본 크라우드소싱 플랫폼 Lancers에 공개된 IT·프로그래밍 의뢰를 제한적으로 수집하고, 일본어 원문을 구조화·분류·분석하여 반복되는 고객 문제와 제품 기회를 찾는 서비스다.

단순한 공고 검색기가 아니라 다음 질문에 답하는 개인용 시장조사 도구를 지향한다.

- 일본 고객이 반복해서 해결하려는 업무 문제는 무엇인가?
- 어떤 업종과 기능에서 개발 수요가 증가하는가?
- 고객이 명시한 예산과 제안 경쟁 수준은 어떠한가?
- 어떤 요구사항을 공통 모듈이나 마이크로 SaaS로 표준화할 수 있는가?
- 1인 개발자가 미리 준비하면 외주 의뢰에 빠르게 대응할 수 있는 분야는 무엇인가?

### 1.2 한 줄 소개

> 일본의 실제 IT 외주 의뢰를 원문 그대로 구조화하고 분석해, 1인 개발자가 준비할 고객 문제와 제품 기회를 보여주는 니즈 레이더

### 1.3 핵심 처리 흐름

```text
Lancers 공개 의뢰
→ 저부하 수집
→ 일본어 원문 정규화
→ 검색 태그와 일본어 분석 결과 생성
→ 수요·예산·경쟁·추세 분석
→ 1인 개발 적합 제품 후보 제안
→ 사용자가 근거를 검토하고 판단
```

## 2. 추진 배경

### 2.1 사용자 상황

주 사용자는 Java 기반 객체지향 개발에 익숙한 25년차 개발자로, 1인 개발자로 독립하기 위해 다양한 마이크로 웹서비스를 무료 MVP로 출시하고 반응이 확인된 제품을 유료화·모바일 앱으로 확장하려 한다.

기술 구현 경험은 충분하지만 실제 업무 현장의 도메인 지식과 사용자가 돈을 지불할 정도로 강한 문제에 관한 정보가 부족하다.

### 2.2 해결하려는 문제

- 제품 아이디어가 실제 고객 수요에서 출발했는지 확인하기 어렵다.
- 일본 외주 의뢰를 매번 직접 읽고 비교·분류하기에는 시간과 정리 비용이 크다.
- 의뢰 내용이 비정형 일본어 문장으로 작성되어 비교와 집계가 어렵다.
- 한두 건의 인상적인 의뢰를 시장 전체의 신호로 오해하기 쉽다.
- 반복 수요와 일회성 맞춤 구축을 구분하기 어렵다.
- 시장성은 있어도 1인 개발자가 운영하기 어려운 아이템일 수 있다.

### 2.3 해결 방향

실제로 예산과 요구사항이 제시된 의뢰를 축적하고, 원문 사실·규칙 기반 정규화·AI 해석을 구분하여 제공한다. 단순 빈도뿐 아니라 예산, 최근 증가세, 제안 경쟁, 표준화 가능성, MVP 크기, 운영 부담을 함께 평가한다.

## 3. 목표와 범위

### 3.1 서비스 목표

1. Lancers IT·시스템 개발 의뢰의 공개 업무 정보를 재현 가능하게 구조화한다.
2. 검색 결과 1~100페이지를 중단·재개 가능한 방식으로 초기 적재한다.
3. 목록 첫 페이지에서 신규 의뢰를 낮은 빈도로 탐지한다.
4. 각 의뢰에 검색용 태그를 최대 10개 부여한다.
5. 일본어 원문을 보존하고 분석 결과도 일본어로 제공한다.
6. 반복 니즈, 예산, 경쟁도, 기술 수요와 제품 기회를 대시보드에서 분석한다.
7. 모든 인사이트를 근거 의뢰까지 추적할 수 있게 한다.

### 3.2 MVP 성공 기준

- 샘플 목록·상세 페이지의 필수 필드를 95% 이상 안정적으로 추출한다.
- 동일 의뢰를 중복 저장하지 않고 신규·변경 여부를 판별한다.
- 모든 프로젝트에 0~10개의 품질 기준을 통과한 태그가 연결된다.
- 기간, 업종, 예산, 기능, 기술, 경쟁 수준으로 검색·필터링할 수 있다.
- 분석 결과에서 일본어 원문과 원본 링크를 바로 확인할 수 있다.
- UI는 i18n 구조를 적용하고 일본어·한국어·영어 메시지 사전을 독립적으로 확장할 수 있다.
- 인사이트마다 표본 수와 근거 프로젝트가 표시된다.
- 매주 최소 1개의 검토할 만한 제품 기회 후보를 얻는다.

### 3.3 MVP 제외 범위

- Lancers 회원에게 자동으로 제안하거나 메시지를 보내는 기능
- 로그인, CAPTCHA 또는 접근 제한 우회
- 발주자·수주자·제안자의 개인정보 및 프로필 수집
- 첨부파일, 제안서, 포트폴리오 다운로드
- Lancers 원문을 대체하는 공개 미러 서비스
- 자동 견적·자동 계약·자동 지원
- AI가 생성한 사업 아이디어의 자동 실행
- 초기 단계의 다중 사용자와 조직 권한 관리

## 4. 수집 정책과 안전 원칙

### 4.1 이용 정책 확인 게이트

실제 자동 수집을 활성화하기 전에 Lancers의 최신 이용약관, robots 정책, 공개 페이지 안내와 관련 법률을 확인한다. 공개 열람이 가능하다는 사실만으로 자동 수집과 장기 저장이 허용된다고 가정하지 않는다.

허용 범위가 불분명하면 다음 대체 경로를 사용한다.

- 소량의 샘플을 수동 입력하여 분석 기능부터 검증
- 사용 허가를 받은 데이터 또는 공식 제공 수단 활용
- 원문 전체 대신 최소 메타데이터와 사용자가 작성한 분석만 보존
- 자동 수집 Kill Switch를 기본적으로 비활성 상태로 유지

### 4.2 저부하 수집 정책

자동 수집이 허용된 범위에서만 다음 제한을 적용한다.

| 항목 | 기본 정책 |
|---|---:|
| 동시 요청 | 1개 |
| 요청 간 최소 간격 | 3초 |
| 권장 실제 간격 | 3~5초 랜덤 지연 |
| 증분 확인 주기 | 30~60분 |
| 타임아웃 | 15초 |
| 네트워크 재시도 | 최대 2회 |
| HTTP 403·429 | 즉시 중단 후 사람 확인 |
| CAPTCHA·로그인 요구 | 우회하지 않고 중단 |

3초는 목표 속도가 아니라 최소 간격이다. 초기 1~100페이지 적재는 체크포인트를 저장해 여러 실행으로 나누고, 목록에서 새 ID를 발견했을 때만 상세 페이지를 요청한다.

### 4.3 최대 수집 원칙과 개인정보 제외

수집이 허용된 범위 안에서는 특정 분석 항목만 선별하지 않고, 공개 페이지에서 확인되는 **프로젝트 단위 정보와 집계 정보는 가능한 한 모두 수집**한다. 현재 분석에 사용하지 않는 필드도 향후 분석 가능성을 위해 원문 값, 정규화 값, 수집 시각과 출처 위치를 함께 보존한다.

파서에 아직 정식 컬럼이 없는 공개 항목은 버리지 않고 `project_attributes`에 레이블·원문 값으로 저장한다. 단, 사람을 식별하거나 접촉하는 데 사용될 수 있는 정보는 공개되어 있어도 수집하지 않는다.

**수집 대상**

- 식별·출처: Lancers 의뢰 ID, 원본 URL, canonical URL, 목록 페이지 번호와 순번
- 분류: 대분류, 중분류, 소분류, 발주 업종, 작업 종류, 공개 카테고리·검색 태그
- 제목·내용: 제목, 부제, 의뢰 개요, 요구사항, 작업 범위, 배경, 목적, 기대 결과, 주의사항
- 계약 조건: 계약·보수 방식, 제시 예산의 원문·최솟값·최댓값·통화, 세금 포함 여부, 지급 조건
- 일정: 공개일, 모집 시작·마감일, 모집 기간, 희망 착수일, 납기, 작업 기간, 일정 협의 가능 여부
- 모집 결과: 모집 상태, 제안 수, 모집 인원, 당선 인원, 예약 인원 등 공개된 프로젝트 단위 집계값
- 성과물: 납품물, 파일 형식, 수량, 품질 조건, 검수·완료 기준, 저작권·재사용 조건
- 기술 조건: 명시된 언어, 프레임워크, 플랫폼, 인프라, 외부 API, 도구, 개발 환경
- 지원 조건: 요구 경험, 필수·우대 조건, 작업 장소·원격 여부, 커뮤니케이션 방식, 지원 시 제출 항목
- 운영 조건: 유지보수, 하자보수, 보안, 비밀유지, 개인정보 처리, 규제·심사 관련 요구
- 참고 정보: 공개된 참고 URL의 주소·도메인·링크 문구, 관련 프로젝트 유형
- 화면 메타데이터: 구조화 데이터(JSON-LD), meta 태그, 공개 배지, 표시 상태, 페이지 언어
- 관찰 이력: 최초 발견일, 마지막 확인일, 상태 변경일, 콘텐츠 해시, 파서 버전
- 파생 정보: 일본어 분석 요약, 최대 10개 표준 태그, 니즈·기능·기술 분류와 신뢰도
- 미정형 공개 필드: 위 목록에 없는 프로젝트 단위 레이블과 값

**수집 제외 대상**

- 발주자, 실제 수주자, 제안자 이름과 닉네임
- 프로필 소개, 프로필 이미지, 프로필 URL
- 전화번호, 이메일, 메신저 ID, 주소
- 개별 제안 내용과 제안 금액
- 첨부파일, 포트폴리오, 신원 인증 정보
- 쿠키, 세션, 인증 토큰

참고 URL은 링크 자체와 도메인만 보존하며, 링크된 외부 사이트를 자동으로 추가 크롤링하지 않는다. 이미지와 첨부파일은 URL·MIME 유형·표시 문구 같은 메타데이터만 필요한 경우 보존하고 바이너리 파일은 내려받지 않는다.

의뢰 본문에 연락처나 개인 식별정보가 포함될 수 있으므로 저장 전에 패턴 기반 마스킹을 수행한다. 마스킹 전 원문은 로그에 남기지 않는다.

### 4.4 비공개 보존 원칙

- 서비스와 DB는 본인만 접근할 수 있게 한다.
- 허용 범위에서는 개인정보를 제거한 프로젝트 본문과 파싱 가능한 공개 필드를 최대한 보존한다.
- 정규화 필드와 함께 수집 당시의 개인정보 제거 원문 스냅샷 또는 구조화 스냅샷을 보존한다.
- HTML 전체가 필요하면 스크립트, 쿠키 값, 추적 파라미터와 사용자 영역을 제거한 정제본만 저장한다.
- 이미지와 첨부파일 바이너리는 저장하지 않고 필요한 메타데이터만 저장한다.
- 프로젝트 단위로 원문, 태그, 분석을 함께 삭제할 수 있어야 한다.
- 외부 공개나 상용화를 검토할 때는 데이터 사용 권한을 별도로 재검토한다.

## 5. 핵심 사용자와 사용 시나리오

### 5.1 초기 사용자

서비스 소유자인 1인 개발자 한 명이다. 일본 시장의 실제 개발 수요를 빠르게 이해하고 제품 아이디어와 외주 대응 자산을 준비하는 데 사용한다.

### 5.2 주요 시나리오

#### A. 최신 수요 확인

최근 24시간과 7일간 등록된 의뢰, 새로 등장한 기술·기능, 예산 변화와 제안 경쟁도를 확인한다.

#### B. 일본어 의뢰 빠르게 이해

일본어 분석 요약과 태그로 의뢰를 선별한 뒤 관심 있는 항목의 원문과 원본 페이지를 검토한다.

#### C. 반복 니즈 탐색

`業務自動化`, `予約管理`, `EC`, `生成AI` 같은 태그를 선택해 관련 업종, 예산, 요구 기능과 추세를 비교한다.

#### D. 제품 기회 찾기

반복 수요가 있고 표준화 가능성이 높으며 1인이 MVP와 운영을 감당할 수 있는 의뢰군을 찾는다.

#### E. 외주 대응 자산 준비

자주 등장하는 인증, 관리자, 결제, 예약, 알림, 데이터 연동 등의 공통 모듈 개발 우선순위를 정한다.

#### F. 근거 검증

AI가 제안한 제품 아이디어의 근거 프로젝트, 원문, 예산과 표본 수를 직접 확인하고 채택·관찰·보류한다.

## 6. 단계별 제품 계획

## Phase 0. 데이터 수집 기반

### 목적

Lancers의 공개 프로젝트 정보를 안전하고 반복 가능하게 수집·정제한다.

### 핵심 기능

- 이용 정책 확인 상태와 Kill Switch
- 목록·상세 페이지 파서
- 검색 결과 1~100페이지 초기 적재
- 첫 페이지 신규 프로젝트 증분 수집
- 프로젝트 ID 기반 중복 방지
- 콘텐츠 해시 기반 변경 감지
- 일본어 텍스트 정규화
- 개인정보 탐지·마스킹

## 7. 수집·정제 설계

### 7.1 수집 흐름

```text
배치 시작
→ 정책 확인 상태와 Kill Switch 검사
→ 목록 페이지 1회 요청
→ 프로젝트 ID·목록 메타데이터 추출
→ 기존 ID·콘텐츠 해시 비교
→ 신규 또는 변경 의심 상세 페이지만 순차 요청
→ 개인정보 마스킹
→ Zod 스키마 검증
→ 일본어 원문·정규화 필드·미정형 공개 속성 저장
→ 태그·분석 작업 등록
→ 실행 결과와 체크포인트 기록
```

### 7.2 초기 적재

1. 사용자가 초기 적재를 명시적으로 시작한다.
2. 목록 1~100페이지를 순서대로 처리한다.
3. 매 요청은 3~5초 랜덤 간격으로 하나씩 실행한다.
4. 일정 요청 수마다 추가 휴지 시간을 둔다.
5. 페이지별 체크포인트를 기록한다.
6. 중단되면 마지막 완료 페이지 다음부터 재개한다.
7. 목록 적재와 상세 적재를 별도 저속 작업으로 분리한다.

### 7.3 증분 수집

- 기본 30~60분 간격으로 목록 1페이지만 확인한다.
- 마지막으로 본 프로젝트 ID를 만나면 탐색을 종료한다.
- 신규 프로젝트만 상세 조회한다.
- 기존 프로젝트의 상태 변경은 더 낮은 빈도의 별도 배치로 확인한다.
- 매 실행에서 최대 요청 수와 최대 실행 시간을 제한한다.

### 7.4 신규·변경 판별

- Lancers 프로젝트 ID를 외부 고유키로 사용한다.
- 분석 대상 필드를 정규화한 뒤 콘텐츠 해시를 생성한다.
- 같은 ID와 같은 해시는 `lastSeenAt`만 갱신한다.
- 해시가 달라지면 새 스냅샷을 추가한다.
- 목록에서 사라졌다고 즉시 삭제하지 않고 `unknown` 상태로 둔다.

### 7.5 파서 내구성

- CSS 클래스 하나에만 의존하지 않고 레이블과 문서 구조를 함께 사용한다.
- 일본어 전각·반각 문자와 공백을 정규화한다.
- 엔화 범위, 건별·시간별·고정 보수를 구분한다.
- 날짜의 원문 문자열과 정규화한 시간을 함께 관리한다.
- 알 수 없는 값은 추정하지 않고 `null`과 파싱 경고로 남긴다.
- 스냅샷에 파서 버전을 기록한다.
- 처음 보는 레이블은 `project_attributes`에 원문 그대로 보존하고 데이터 품질 경고를 남긴다.
- JSON-LD와 공개 meta 태그를 별도로 추출해 화면 파싱 결과와 교차 검증한다.

### 7.6 수집 필드 완전성 관리

- 상세 페이지에 등장한 공개 레이블 목록을 페이지별로 기록한다.
- 알려진 레이블, 새 레이블, 제외 레이블, 개인정보 의심 레이블로 분류한다.
- 새 레이블은 원문 속성으로 우선 저장한 뒤 정식 컬럼 승격 여부를 검토한다.
- 각 스냅샷에 `discoveredFieldCount`, `storedFieldCount`, `excludedFieldCount`를 기록한다.
- 저장하지 않은 필드는 제외 이유를 `collection_exclusions`에 기록한다.
- 목록과 상세 페이지의 동일 항목은 각각 원문을 보존하고 불일치를 데이터 품질 경고로 표시한다.

## 8. 검색 태그 설계

### 8.1 태그 목적

태그는 원문을 대체하는 요약이 아니라 검색과 집계를 위한 제한된 분류값이다. 프로젝트마다 최대 10개만 저장해 태그가 과도하게 분산되는 것을 방지한다.

### 8.2 태그 분류

| 유형 | 예시 |
|---|---|
| 업종 | 교육, 의료, 부동산, EC, 제조 |
| 제품 형태 | 웹서비스, 모바일 앱, 관리자, API, 배치 |
| 핵심 기능 | 예약, 결제, 채팅, 검색, 알림, 리포트 |
| 기술 | Java, PHP, Python, React, AWS |
| 업무 목적 | 자동화, 신규 구축, 리뉴얼, 데이터 연동 |
| 데이터·AI | 생성 AI, 챗봇, OCR, 추천, 분석 |

### 8.3 태그 생성 절차

1. Lancers 카테고리와 명시된 기술을 규칙 기반 태그로 추출한다.
2. 제목과 의뢰 개요에서 핵심 기능과 목적 후보를 추출한다.
3. 태그 사전의 표준 태그로 정규화한다.
4. 근거 문구가 없는 태그는 생성하지 않는다.
5. 중요도와 검색 가치 순으로 최대 10개를 선택한다.
6. 각 태그에 생성 방식과 신뢰도를 기록한다.

### 8.4 태그 품질 원칙

- 일본어 동의어는 하나의 표준 태그에 연결한다.
- `開発`, `システム`처럼 지나치게 넓은 단어만으로 태그를 만들지 않는다.
- 고객이 지정한 기술과 분석기가 추정한 기술을 구분한다.
- 태그 사전 변경 시 기존 프로젝트를 재분석할 수 있어야 한다.
- 사용자가 잘못된 태그를 수정하고 제외 규칙을 등록할 수 있어야 한다.

## 9. 언어와 분석 체계

### 9.1 콘텐츠 언어 원칙

| 데이터 | 역할 |
|---|---|
| 일본어 원문 | 출처 사실과 근거 |
| 정규화 일본어 | 검색·해시·분석 입력 |
| 일본어 분석 요약 | 문제, 요구 기능, 사업 관점 해석 |

Lancers에서 수집한 콘텐츠는 번역하지 않는다. 제목, 본문, 태그, 니즈 클러스터, 제품 기회 설명과 AI 분석 결과를 일본어로 저장·표시한다. UI 언어를 한국어나 영어로 바꾸더라도 수집 콘텐츠는 일본어 원문을 유지한다.

### 9.2 웹 UI i18n 원칙

- 기본 로케일은 `ja`, 추가 지원 로케일은 `ko`, `en`으로 한다.
- 메뉴, 버튼, 필터명, 상태, 오류, 도움말 같은 UI 메시지만 번역 사전으로 관리한다.
- URL은 `/{locale}/...` 형식을 사용한다. 예: `/ja/projects`, `/ko/projects`, `/en/projects`.
- `app/[locale]` 아래에 페이지와 레이아웃을 배치하고 지원하지 않는 로케일은 404 처리한다.
- 최초 루트 접근은 브라우저 언어와 저장된 사용자 설정을 확인하되 기본값은 일본어다.
- 날짜, 숫자, 통화는 `Intl.DateTimeFormat`과 `Intl.NumberFormat`으로 로케일에 맞게 표시한다.
- JPY 원본 금액과 일본 시간대 의미는 UI 로케일 변경으로 변형하지 않는다.
- 메시지 키는 화면 문구와 분리하고 `ja`, `ko`, `en` 사전의 키 일치 여부를 빌드 시 검증한다.
- 메시지 사전은 서버에서 로딩해 기본 번들을 클라이언트에 모두 포함하지 않는다.
- 수집 데이터 자체의 다국어 컬럼은 만들지 않는다. 향후 콘텐츠 번역이 필요해질 때 별도 파생 테이블로 추가한다.

### 9.3 분석 단위

- 고객이 해결하려는 핵심 문제
- 발주 업종과 대상 사용자
- 요청 제품과 성과물
- 필수 기능과 선택 기능
- 지정 기술과 기술 제약
- 예산과 납기
- 신규 구축·리뉴얼·유지보수 구분
- 외부 서비스 연동
- 보안·규제·운영 위험
- 표준 제품화 가능 요소

### 9.4 제안 경쟁 분석

제안 수는 시장 수요가 아니라 해당 의뢰에 대한 공급 경쟁 신호다. 다음 값을 함께 표시한다.

- 제안 수
- 모집 인원과 당선 인원
- 예산 범위
- 모집 기간
- 카테고리
- 유사 프로젝트의 제안 수 중앙값

제안 수가 많다는 이유만으로 좋은 시장이라고 판단하지 않으며, 낮은 단가의 단순 작업이 제안 수를 크게 만들 수 있다는 경고를 표시한다.

### 9.5 니즈 클러스터

LLM은 다음 구조를 제안하되 사실로 확정하지 않는다.

- 핵심 문제
- 대상 업종과 사용자
- 현재 업무 방식
- 요청 기능
- 기대 효과
- 반복 가능한 제품 요소
- 맞춤 구축 요소
- SaaS 전환 가능성

분석 결과에는 모델, 프롬프트 버전, 생성 시각, 근거 프로젝트 ID와 신뢰도를 저장한다. 출력은 Zod Schema로 검증한다.

- `project_tags(project_id, tag_id)` Unique Constraint
- 프로젝트별 활성 태그는 애플리케이션 로직에서 최대 10개로 제한
- `source_type`: `category`, `explicit`, `rule`, `ai`, `user`
- `confidence`: 0~1
- `evidence_text`: 개인정보 제거된 짧은 근거 문구
- 사용자 확정 태그는 자동 재분석에서 제거하지 않음

## 14. 시스템 구성

```text
Next.js 반응형 웹 (crawllancers-web)
          ↓ 순수 TypeScript API Client
Hono REST API (crawllancers-api, Vercel)
          ↓
수집 / 파싱 / 태깅 / 분석 Use Case
          ↓
Supabase PostgreSQL (crawllancers schema)

Vercel Cron 또는 수동 Trigger
          ↓
체크포인트 기반 저부하 Batch
```

### 14.1 모노레포 구조

```text
apps/
├─ crawllancers-web/
└─ crawllancers-api/

packages/
├─ api-contracts/crawllancers/
├─ api-client-core/
├─ crawllancers-api-client/
├─ database/
├─ auth/
├─ llm/
├─ logging/
└─ batch/

database/
├─ migrations/crawllancers/
└─ seeds/crawllancers/
```

### 14.2 구현 원칙

- 프론트엔드는 DB에 직접 접근하지 않는다.
- 수집·태깅·분석 로직은 백엔드 Use Case에 둔다.
- UI i18n은 웹 애플리케이션의 메시지 사전과 로케일 라우팅으로 처리하며 API의 도메인 데이터를 번역하지 않는다.
- SQL은 직접 작성하고 외부 값은 Parameter Binding한다.
- 파서 입력, 외부 응답, LLM 출력은 `unknown`에서 Zod로 검증한다.
- API Client는 React나 Next.js에 의존하지 않는 순수 TypeScript로 만든다.
- Cron은 실행 계기일 뿐이며 핵심 로직은 일반 Node.js에서도 실행 가능하게 한다.
- 태그 생성과 사업성 평가는 버전 관리하고 재실행 가능하게 한다.

## 16. UX·디자인 방향

### 16.1 화면 톤

- 일본 시장을 관찰하는 개인 연구실 형태
- 정보 밀도는 높지만 원문과 분석의 출처가 명확한 UI
- 기본 UI는 일본어로 제공하고 `ja`, `ko`, `en` 로케일을 동일한 화면 구조로 지원
- 수집 콘텐츠와 분석 결과는 모든 UI 로케일에서 일본어로 표시
- 세부 검증 시 일본어 원문을 나란히 확인
- 분석은 데스크톱에 최적화하고 현황 확인은 모바일 대응

### 16.2 정보 상태 구분

```text
원문 사실:       Slate
규칙 기반 정규화: Blue
AI 분석:         Violet
제품 기회:       Emerald
주의·위험:       Amber
수집 중단:       Red
```

### 16.3 신뢰 표시

- `원문`: Lancers 공개 페이지에서 직접 추출
- `정규화`: 금액·날짜·카테고리를 규칙으로 변환
- `UI 메시지`: 선택한 로케일의 메뉴·버튼·도움말
- `AI 분석`: 원문을 근거로 모델이 제안
- `사용자 확정`: 사용자가 직접 수정·승인

## 19. 테스트 전략

### 정상 테스트

- 목록에서 프로젝트 ID, 제목, 상세 URL을 추출한다.
- 상세에서 업종, 예산, 모집 기간, 의뢰 개요를 정규화한다.
- 정의되지 않은 새 공개 레이블도 `project_attributes`에 보존한다.
- 목록·상세·JSON-LD의 중복 필드를 비교하고 불일치를 경고한다.
- 신규 프로젝트가 한 번만 저장된다.
- 프로젝트당 태그가 최대 10개 생성된다.
- 분석 요약에서 일본어 원문으로 이동할 수 있다.
- 세 로케일에서 같은 프로젝트 데이터와 현지화된 UI가 표시된다.
- 대시보드 집계와 근거 프로젝트 수가 일치한다.

### 경계 테스트

- 예산 협의, 범위형 예산, 건별 보수와 시간 보수를 구분한다.
- 마감일과 납기일을 혼동하지 않는다.
- 제안 수가 없거나 모집 중인 프로젝트를 처리한다.
- 일본어 전각 숫자와 특수문자를 정규화한다.
- 기존 프로젝트 변경 시 스냅샷을 추가한다.
- 10개를 초과한 태그 후보에서 우선순위를 안정적으로 적용한다.

### 실패·안전 테스트

- 본문의 전화번호와 이메일을 저장 전에 마스킹한다.
- 발주자·수주자·제안자 프로필을 저장하지 않는다.
- 저장하지 않은 공개 항목은 제외 이유가 기록된다.
- 403과 429에서 수집을 중단한다.
- CAPTCHA를 우회하지 않는다.
- DOM 구조가 바뀌면 잘못된 값을 저장하지 않는다.
- 동시에 두 배치를 실행하지 않는다.
- Kill Switch가 켜져 있으면 네트워크 요청을 보내지 않는다.
- 잘못된 LLM 태그와 분석 결과가 DB의 원문을 변경하지 않는다.
- 누락되거나 지원하지 않는 로케일과 메시지 키를 안전하게 처리한다.

| 대형 구축을 SaaS로 오해 | 표준화 가능성과 운영 적합도 별도 평가 |
| 일본 현지화 비용 과소평가 | 언어·결제·지원 장벽을 독립 평가 |
| 서버리스 실행 시간 초과 | 체크포인트 기반 작은 배치로 분할 |

---

## 21. 핵심 의사결정

1. 초기 서비스는 공개 Lancers 미러가 아니라 본인만 사용하는 비공개 리서치 도구다.
2. 사람이나 계정을 분석하지 않고 프로젝트의 비식별 업무 요구만 분석한다.
3. 수집이 허용된 프로젝트 단위 공개 정보는 현재 사용 여부와 무관하게 원문·정규화 값·출처를 최대한 보존한다.
4. 수집 콘텐츠와 분석 결과는 일본어로 유지하고, 웹 UI 문구만 i18n으로 다국어 지원한다.
5. 프로젝트별 검색 태그는 최대 10개이며 모든 자동 태그에 근거와 신뢰도를 둔다.
6. 요청은 동시 1개, 최소 3초 간격으로 제한하고 제한 신호가 있으면 중단한다.
7. AI 분석은 검토 후보이며 모든 결론은 근거 프로젝트와 표본 수를 제공한다.
8. 성공은 수집량이 아니라 실행 가능한 고객 문제와 제품 가설을 발견했는지로 판단한다.

## 22. 최종 산출물

MVP가 완료되면 다음 결과물을 갖는다.

- Lancers 공개 IT 의뢰의 비식별 업무 데이터 저장소
- 프로젝트 단위 공개 필드의 원문·정규화 값과 미정형 속성 저장소
- 1~100페이지 초기 적재와 첫 페이지 증분 수집 파이프라인
- 프로젝트별 최대 10개의 검색 태그
- 일본어 원문과 일본어 분석 요약을 함께 보는 프로젝트 탐색 화면
- 일본어·한국어·영어 UI를 지원하는 i18n 웹 애플리케이션
- 업종·기능·기술·예산·제안 경쟁 분석 대시보드
- 1인 개발 관점의 제품 기회 후보 목록
- 모든 분석에서 원문 근거로 이동하는 추적 구조
- 후보를 채택·관찰·보류하고 메모하는 개인 연구 워크플로

서비스의 최종 성공 기준은 다음 질문에 정기적으로 더 좋은 답을 제공하는 것이다.
