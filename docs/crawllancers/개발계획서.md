# CrawlLancers 개발계획서

> 코딩 에이전트가 `서비스기획서.md`를 기준으로 CrawlLancers MVP를 단계별 구현하기 위한 실행 계획

- 문서 버전: v1.0
- 작성일: 2026-08-02
- 프로젝트 코드: `crawllancers`
- 기준 문서: `docs/crawllancers/서비스기획서.md`
- 기본 콘텐츠 언어: 일본어
- 웹 UI 지원 로케일: `ja`, `ko`, `en`

---

## 1. 개발 목표

Lancers의 공개 IT·시스템 개발 의뢰에서 허용된 프로젝트 단위 정보를 저부하로 수집하고, 일본어 원문을 검색·분류·분석하여 1인 개발자가 제품 기회를 찾을 수 있는 비공개 웹서비스를 구현한다.

MVP는 다음 흐름을 완성해야 한다.

```text
관리자 로그인
→ 수집 정책 확인
→ 1~100페이지 초기 적재 또는 첫 페이지 증분 수집
→ 상세 정보·미정형 공개 필드 저장
→ 개인정보 마스킹과 최대 10개 태그 생성
→ 일본어 검색·분석
→ 대시보드와 제품 기회 검토
```

## 2. 에이전트가 먼저 읽을 자료

구현 전에 다음 파일을 순서대로 읽는다.

1. 저장소 루트의 현재 지시 파일
2. `docs/crawllancers/배경.md`
3. `docs/crawllancers/서비스기획서.md`
4. 루트 `package.json`, `pnpm-workspace.yaml`, `tsconfig.base.json`
5. 기존 `packages/database`, `packages/api-client-core` 구현
6. 기존 서비스의 API·웹 구조 중 재사용 가능한 패턴

기존 사용자 변경을 덮어쓰지 않는다. 신규 서비스에 필요한 파일만 추가하고 공통 패키지를 수정할 때는 기존 서비스의 빌드가 깨지지 않는지 확인한다.

## 3. 확정 기술 스택

| 영역 | 기술 |
|---|---|
| 언어 | TypeScript |
| 패키지 관리 | pnpm workspace |
| 웹 | Next.js App Router, React, Tailwind CSS |
| API | Hono, Node.js Runtime |
| 입력 검증 | Zod |
| DB | Supabase PostgreSQL, 직접 SQL |
| DB Driver | 기존 `packages/database`가 사용하는 PostgreSQL Driver |
| 배포 | Vercel |
| 스케줄 | Vercel Cron Adapter + 일반 Batch Use Case |
| 테스트 | 저장소 기존 도구 우선, 없으면 Vitest 검토 |

추가 라이브러리는 실제 필요성이 확인될 때만 도입한다. i18n은 우선 Next.js 공식 App Router 패턴인 `[locale]` 라우팅과 서버 전용 JSON 사전으로 구현한다. 요구사항이 복잡해질 때만 `next-intl` 같은 라이브러리를 검토한다.

## 5. 중요한 아키텍처 결정

### 5.1 웹과 API 분리

- 웹은 Hono REST API만 호출한다.
- 웹에서 Supabase 업무 테이블에 직접 접근하지 않는다.
- Next.js Server Action과 Route Handler에 수집·분석 비즈니스 로직을 작성하지 않는다.
- 웹의 서버 컴포넌트도 `crawllancers-api-client`를 통해 API를 호출한다.

### 5.2 데이터베이스 접근

- `crawllancers` PostgreSQL Schema는 Supabase Data API에 노출하지 않는다.
- Hono API가 서버 전용 DB 연결로 직접 SQL을 실행한다.
- 브라우저에 DB 연결 문자열, Supabase Secret Key 또는 Service Role Key를 노출하지 않는다.
- 모든 SQL 외부 값은 Parameter Binding한다.
- 테이블·컬럼·정렬 방향 같은 동적 식별자는 허용 목록으로 검증한다.
- 방어 심층화가 필요한 테이블은 RLS를 적용하되 API의 서버 DB 역할과 충돌하지 않게 테스트한다.

Supabase의 2026년 변경사항을 고려해 새 테이블이 Data API에 자동 노출된다고 가정하지 않는다. 이 서비스는 직접 DB 접근 모델이므로 해당 Schema를 노출 목록에 추가하지 않는다.

### 5.3 콘텐츠 언어와 UI 언어 분리

- Lancers 제목, 본문, 태그, 니즈와 AI 분석 결과는 일본어다.
- 번역 API나 번역 컬럼은 MVP에 만들지 않는다.
- `ja`, `ko`, `en`은 메뉴, 버튼, 필터, 상태, 오류, 도움말 같은 UI 메시지만 바꾼다.
- UI 로케일을 바꾸어도 프로젝트 데이터와 검색 대상은 일본어로 유지한다.
- 날짜, 숫자, 통화 표시만 현재 UI 로케일의 `Intl` 형식을 사용한다.
- 저장되는 금액은 JPY 정수이며 원문 문자열도 함께 보존한다.

### 5.4 수집 실행 경계

- 정책 확인이 완료되지 않으면 네트워크 수집을 실행하지 않는다.
- 동시 요청은 1개다.
- 요청 간 최소 3초, 기본 3~5초 랜덤 지연을 적용한다.
- 403, 429, CAPTCHA, 로그인 요구에서는 즉시 중단한다.
- 우회·프록시 회전·CAPTCHA 해결 기능을 구현하지 않는다.
- 배치는 체크포인트와 Idempotency를 가져야 한다.

### 6.1 Migration 순서

### 6.2 핵심 테이블

#### `crawllancers.projects`

현재 상태와 자주 조회하는 정규화 필드를 저장한다.

- 내부 ID와 Lancers 프로젝트 ID
- 원본·canonical URL
- 일본어 제목과 본문
- 분류, 업종, 계약 방식
- JPY 예산 원문·최소·최대·세금 정보
- 공개·모집·희망 착수·납기 일정
- 제안·모집·당선·예약 인원 집계
- 성과물·필수 기술·우대 기술
- 작업 장소·원격·커뮤니케이션 방식
- 지원·유지보수·보안·저작권 조건
- 상태, 최초·마지막 발견일, 상태 변경일
- 콘텐츠 해시와 파서 버전

#### `project_snapshots`

- 변경 전후 비교를 위한 불변 스냅샷
- 개인정보를 제거한 일본어 원문
- 목록·상세·JSON-LD·meta 추출 결과 JSONB
- 콘텐츠 해시와 수집 시각
- 파서 버전

#### `project_attributes`

- 정식 컬럼에 없는 공개 레이블과 값
- 원문 섹션, 일본어 레이블, 개인정보 제거 값
- 정규화 키·값과 발견 시각

#### `project_links`, `project_asset_metadata`

- 참고 URL, 도메인, 링크 문구
- 이미지·첨부파일의 URL·MIME·표시 문구만 저장
- 외부 링크 추가 크롤링과 바이너리 다운로드 금지

#### `tags`, `tag_aliases`, `project_tags`

- 일본어 표준 태그와 동의어
- 프로젝트당 활성 태그 최대 10개
- 생성 출처, 신뢰도, 근거 문구
- 사용자 확정 태그 보호

#### `crawl_runs`, `crawl_failures`

- 실행 유형: `INITIAL_LIST`, `INITIAL_DETAIL`, `INCREMENTAL`, `REFRESH`
- 상태: `PENDING`, `RUNNING`, `PAUSED`, `SUCCEEDED`, `FAILED`, `POLICY_STOPPED`
- 체크포인트 페이지와 프로젝트 ID
- 요청·성공·실패·신규·변경 건수
- 다음 실행 가능 시각과 중단 사유

#### 분석 테이블

- `need_clusters`
- `project_need_clusters`
- `opportunities`
- `opportunity_evidence`
- `analysis_runs`
- `review_notes`

### 6.3 인덱스

- `projects.external_project_id` Unique
- `projects.published_at`, `first_seen_at`, `source_status`
- `projects.budget_min_jpy`, `budget_max_jpy`, `proposal_count`
- 카테고리와 업종
- `project_tags(project_id, tag_id)` Unique
- 태그별 프로젝트 조회 인덱스
- 일본어 검색을 위한 PostgreSQL 검색 전략은 샘플 데이터로 검증 후 결정

일본어 형태소 분석 확장을 섣불리 추가하지 않는다. MVP는 정규화 문자열의 `ILIKE`, 태그, 제목 검색으로 시작하고 성능·검색 품질이 부족할 때 n-gram 또는 외부 검색엔진을 검토한다.

## 7. API 계약 구현 계획

### 7.1 공통 규칙

성공 응답:

```json
{
  "success": true,
  "data": {},
  "meta": { "requestId": "..." }
}
```

오류 응답:

```json
{
  "success": false,
  "error": {
    "code": "CRAWL_POLICY_NOT_CONFIRMED",
    "message": "...",
    "details": null
  },
  "meta": { "requestId": "..." }
}
```

- 오류 처리는 메시지가 아니라 오류 코드 기준이다.
- 요청·응답 Schema는 `packages/api-contracts/crawllancers`에 Zod로 정의한다.
- DB Row 타입은 공개 계약에 포함하지 않는다.
- API의 도메인 데이터는 일본어로 반환한다.
- API 오류 `message`는 안정적인 코드의 보조 설명이며 웹에서 i18n 메시지로 변환한다.

## 8. Lancers Adapter와 파서 계획

### 8.1 Adapter 책임

`adapters/lancers`는 다음만 담당한다.

- 목록·상세 URL 생성
- HTTP 요청과 User-Agent 식별
- 최소 3초 지연과 재시도
- 응답 상태·콘텐츠 유형 검사
- HTML을 파서에 전달
- CAPTCHA·로그인·접근 제한 탐지

태깅이나 사업 판단은 Adapter에 넣지 않는다.

### 8.2 파서 출력

```typescript
type ParsedLancersProject = {
  project: NormalizedProjectInput;
  attributes: ParsedAttribute[];
  links: ParsedLink[];
  assets: ParsedAssetMetadata[];
  source: {
    listFields?: unknown;
    detailFields: unknown;
    jsonLd?: unknown;
    meta?: unknown;
  };
  warnings: ParseWarning[];
};
```

실제 타입은 Zod Schema에서 추론한다.

### 8.3 필드 완전성

- 목록과 상세 페이지에 나타난 모든 공개 레이블을 기록한다.
- 알려진 필드는 정식 필드로 정규화한다.
- 새로운 레이블은 `project_attributes`에 저장한다.
- 제외한 필드는 `collection_exclusions`에 이유를 기록한다.
- 목록·상세·JSON-LD 값이 다르면 우선순위 규칙을 적용하고 경고를 남긴다.
- 파서 회귀 Fixture는 개인정보가 제거된 최소 HTML로 저장한다.

### 8.4 개인정보 제거

- 이메일, 전화번호, 주소, SNS·메신저 ID 패턴 마스킹
- 발주자·수주자·제안자 프로필 영역 제거
- 원문 로그 금지
- 마스킹 전 텍스트를 예외 메시지에 포함하지 않음
- 의심 정보가 확실히 제거되지 않으면 저장하지 않고 실패 큐로 이동

## 9. 태깅과 분석 계획

### 9.1 태깅 우선순위

1. Lancers 공개 카테고리
2. 본문에 명시된 기술·제품·기능
3. 규칙 기반 동의어 사전
4. 구조화된 LLM 출력
5. 사용자 수정

프로젝트당 활성 태그는 최대 10개다. LLM 출력은 일본어 태그, 근거 문구, 신뢰도를 Zod로 검증한다.

### 9.2 LLM 적용 범위

- 일본어 핵심 문제 요약
- 요구 기능 분류
- 니즈 클러스터 후보
- 표준화 가능 요소
- 1인 개발 위험 요인
- 제품 기회 후보

번역에는 사용하지 않는다. LLM 호출은 공통 `packages/llm`이 존재하면 재사용하고, Prompt와 출력 Schema는 `crawllancers-api` 기능 폴더에 둔다.

### 9.3 분석의 근거성

- 모든 클러스터와 기회에 근거 프로젝트 ID 저장
- 표본 수가 작으면 경고
- AI 출력이 원문 필드를 수정하지 못하게 분리
- 모델·Prompt·Schema 버전 저장
- 사용자가 수정·보류·채택 가능

## 10. 웹 i18n 구현 계획

### 10.1 지원 로케일

```typescript
export const locales = ['ja', 'ko', 'en'] as const;
export const defaultLocale = 'ja';
export type Locale = (typeof locales)[number];
```

### 10.2 URL 구조

```text
/                  → 사용자 설정 또는 Accept-Language 확인 후 로케일 이동
/ja                → 일본어 UI 대시보드
/ko/projects       → 한국어 UI 프로젝트 목록
/en/opportunities  → 영어 UI 제품 기회
```

- 지원하지 않는 로케일은 `notFound()` 처리한다.
- 언어 전환 시 현재 경로와 Query를 유지한다.
- 사용자가 선택한 로케일을 Cookie에 저장한다.
- 인증·정적 자산·API 경로는 로케일 Redirect 대상에서 제외한다.

### 10.3 메시지 사전

```text
src/i18n/dictionaries/
├─ ja.json
├─ ko.json
└─ en.json
```

키 예시:

```json
{
  "navigation": {
    "dashboard": "...",
    "projects": "...",
    "opportunities": "..."
  },
  "crawlStatus": {
    "running": "...",
    "paused": "...",
    "policyStopped": "..."
  },
  "errors": {
    "PROJECT_NOT_FOUND": "...",
    "CRAWL_POLICY_NOT_CONFIRMED": "..."
  }
}
```

- `ja.json`을 기준 사전으로 사용한다.
- 세 사전은 동일한 키 구조를 가져야 한다.
- 사전은 `server-only` Loader로 동적 import한다.
- 클라이언트 컴포넌트에는 필요한 메시지만 직렬화해 전달한다.
- 도메인 값이나 프로젝트 본문을 사전에 넣지 않는다.
- 번역 문자열에 HTML을 저장하지 않는다.

### 10.4 로케일 포맷터

- 날짜: `Intl.DateTimeFormat(locale, { timeZone: 'Asia/Tokyo' })`
- 금액: `Intl.NumberFormat(locale, { style: 'currency', currency: 'JPY' })`
- 숫자: `Intl.NumberFormat(locale)`
- 상대 시간: 필요할 때 `Intl.RelativeTimeFormat`

원본 시각의 의미를 보존하기 위해 수집·게시 일정은 DB에 `timestamptz`로 저장하고 화면에서는 명시적으로 `Asia/Tokyo`를 사용한다.

### 10.5 i18n 테스트

- 모든 메시지 사전 키가 동일하다.
- `/ja`, `/ko`, `/en`의 핵심 페이지가 렌더링된다.
- 언어 전환 후 경로와 필터가 유지된다.
- `<html lang>`이 현재 로케일과 일치한다.
- 일본어 프로젝트 콘텐츠는 모든 로케일에서 변하지 않는다.
- JPY와 날짜가 로케일에 맞게 표시된다.
- 지원하지 않는 로케일이 안전하게 처리된다.

## 12. 인증과 보안

### 12.1 MVP 인증

비공개 단일 사용자 서비스이므로 Supabase Auth 이메일 로그인을 사용하거나 기존 공통 `packages/auth`가 지원하는 방식 중 가장 단순한 방식을 선택한다.

- 공개 회원가입 비활성화
- 허용된 관리자 사용자 ID 또는 이메일을 서버 설정으로 제한
- API에서 Access Token을 검증
- 웹 UI 보호만으로 끝내지 않고 모든 관리자 API에서 권한 확인
- 권한 판단에 사용자 수정 가능한 `user_metadata`를 사용하지 않음
- 필요 시 `app_metadata` 또는 서버의 관리자 Allowlist 사용

### 12.2 비밀정보

- 브라우저: 공개 가능한 Auth Publishable Key만 허용
- 서버: DB URL과 Supabase Secret은 Vercel Server Environment에만 저장
- `NEXT_PUBLIC_` 이름으로 Secret을 만들지 않음
- 로그에 Token, Cookie, DB URL, 원문 개인정보를 기록하지 않음
- `.env.example`에는 값 없이 변수명만 제공

### 12.3 보안 검증

- 인증 없는 API 호출 거부
- 일반 사용자가 수집 실행·삭제 API를 호출하지 못함
- Object ID를 바꿔 다른 데이터에 접근하는 BOLA 테스트
- Rate Limit과 중복 배치 Lock
- SQL Injection 테스트
- API 오류에 Stack Trace와 원문 Payload 미노출

## 16. 에이전트 작업 규칙

### 반드시 지킬 것

- 한 Phase를 완료하고 검증한 뒤 다음 Phase로 이동한다.
- 변경 전 기존 공통 패키지와 유사 구현을 검색한다.
- SQL에 `select *`를 사용하지 않고 필요한 컬럼을 명시한다.

- 프로젝트 콘텐츠를 한국어나 영어로 번역하지 않는다.
- UI 텍스트를 컴포넌트에 하드코딩하지 않고 메시지 사전 키를 사용한다.

- 네트워크 수집은 정책 게이트와 Kill Switch를 통과해야 한다.
- 수집 테스트는 Fixture를 우선하고 실제 사이트 요청을 최소화한다.
- 각 Phase 종료 시 실행한 검증과 남은 위험을 보고한다.

### 하지 말아야 할 것

- ORM 도입
- 웹에서 업무 DB 직접 접근
- 핵심 로직을 Next.js Server Action에 작성
- Supabase Trigger·Edge Function에 수집·분석 정책 구현
- 로그인·CAPTCHA·접근 제한 우회
- 발주자·수주자·제안자 프로필 수집
- 이미지·첨부파일 바이너리 다운로드
- 공개되지 않은 API 추측 사용

- 검증하지 않은 라이브러리 대량 도입

- 실제 사이트 자동 수집은 실행하지 않는다.

확정 원칙:
- Next.js App Router 웹과 Hono API를 분리한다.
- Supabase PostgreSQL의 crawllancers Schema를 사용한다.
- SQL을 직접 작성하고 Parameter Binding한다.
- 콘텐츠와 분석 결과는 일본어로 유지한다.
- UI만 i18n으로 ja, ko, en을 지원하며 기본 로케일은 ja다.
- 프로젝트당 검색 태그는 최대 10개다.
- 수집은 동시 1개, 최소 3초 간격이며 제한 신호에서 즉시 중단한다.
- 사람의 이름, 프로필, 연락처와 개별 제안 내용은 수집하지 않는다.
