# CrawlKmong 서비스 기획서

> 크몽 IT·프로그래밍 의뢰 데이터를 바탕으로 고객 니즈와 1인 개발자의 사업 기회를 발견하는 개인용 리서치 도구

- 문서 버전: v1.0
- 작성일: 2026-08-02
- 프로젝트 코드: `crawlkmong`
- 사용 범위: 개발자 본인의 비공개·개인적 분석 용도

---

## 1. 서비스 개요

### 1.1 서비스 정의

CrawlKmong은 크몽의 IT·프로그래밍 프로젝트 의뢰에서 공개된 업무 요구사항을 제한적으로 수집하고 구조화하여, 반복되는 고객 문제와 기술 수요를 분석하는 개인용 웹서비스다.

이 서비스의 목적은 외주 공고를 단순히 모아보는 것이 아니다. 축적된 의뢰를 다음 질문에 답할 수 있는 사업 탐색 자료로 바꾸는 것이 핵심이다.

- 고객이 반복해서 해결하려는 문제는 무엇인가?
- 어떤 업종과 업무에서 소프트웨어 수요가 증가하는가?
- 어떤 요구사항이 여러 프로젝트에 공통으로 나타나는가?
- 1인 개발자가 감당할 수 있는 MVP 또는 마이크로 SaaS 기회는 무엇인가?
- 미리 준비해두면 외주 제안에 빠르게 대응할 수 있는 공통 기능은 무엇인가?

### 1.2 한 줄 소개

> 실제 IT 외주 의뢰를 구조화하고 분석해, 1인 개발자가 준비할 고객 문제와 제품 기회를 찾는 개인용 니즈 레이더

### 1.3 핵심 가치

```text
공개 의뢰 수집
→ 요구사항 구조화
→ 반복 니즈·예산·기술 수요 분석
→ 제품 아이디어 후보 생성
→ 사람이 검토하고 실행 후보 선정
```

## 2. 배경과 문제 정의

### 2.1 사용자 배경

주 사용자는 Java 기반 객체지향 개발 경험이 풍부한 25년차 개발자이며, 현재 1인 개발자로 독립하기 위해 여러 마이크로 웹서비스의 무료 MVP를 출시하려 한다.

기술 구현 능력은 충분하지만 실제 업무 현장의 도메인 지식과 사용자가 비용을 지불할 만큼 강한 문제에 대한 정보가 부족하다.

### 2.2 현재 문제

- 제품 아이디어가 실제 고객 수요에서 출발했는지 검증하기 어렵다.
- 외주 의뢰를 일일이 읽으면 시간에 따라 변화하는 패턴을 발견하기 어렵다.
- 요구사항, 예산, 일정, 기술 스택이 비정형 텍스트에 섞여 있다.
- 한두 건의 인상적인 의뢰를 시장 전체의 신호로 오해할 수 있다.
- 1인 개발자가 수행 가능한 기회와 팀 단위 대형 구축 사업을 구분하기 어렵다.

### 2.3 해결 방향

실제로 비용 지불 의사가 표현된 외주 의뢰를 지속적으로 축적하고, 원문 사실과 분석 결과를 분리해 제공한다. 빈도뿐 아니라 예산, 최근 증가세, 반복성, 표준화 가능성, 1인 개발 적합성을 함께 평가한다.

## 3. 서비스 목표와 범위

### 3.1 목표

1. IT·프로그래밍 의뢰의 공개 업무 정보를 재현 가능하게 구조화한다.
2. 신규 의뢰를 낮은 빈도로 탐지하고 변경 이력을 보존한다.
3. 반복되는 고객 문제, 기능, 업종, 기술 수요를 정량·정성 분석한다.
4. 분석 결과를 1인 개발 관점의 제품 기회와 준비 과제로 변환한다.
5. 각 인사이트가 어떤 원문 데이터에서 도출됐는지 추적 가능하게 한다.

### 3.2 MVP 성공 기준

- 샘플 상세 페이지의 주요 비개인정보 필드를 안정적으로 추출한다.
- 같은 프로젝트를 중복 저장하지 않고 신규·변경 여부를 판별한다.
- 분석 대시보드에서 기간, 업종, 예산, 기능, 기술 스택으로 필터링할 수 있다.
- 모든 인사이트에서 근거가 된 프로젝트 목록으로 이동할 수 있다.
- 사용자가 매주 최소 1개의 검토할 만한 제품 아이디어 후보를 얻는다.

### 3.3 제외 범위

- 크몽 사용자에게 연락하거나 영업 메시지를 자동 발송하는 기능
- 로그인 우회, CAPTCHA 우회, 접근 제한 회피
- 작성자 프로필 수집 및 개인별 행동 추적
- 전화번호, 이메일, 실명 등 개인정보 수집
- 제안서, 포트폴리오, 첨부파일 다운로드
- 크몽 원문을 대체하는 공개 재배포 서비스
- 자동 계약, 자동 지원, 자동 견적 제출
- AI가 생성한 사업 아이디어의 자동 실행

## 4. 운영 원칙과 수집 안전장치

### 4.1 이용 정책 확인

2026-08-02 확인 기준, 크몽 공개 페이지에는 스크래핑 행위를 금지한다는 안내가 표시되어 있다. 개인적·비공개 이용이라고 해서 해당 정책 검토가 면제되는 것은 아니다.

따라서 실제 자동 수집은 다음 조건을 충족한 후에만 활성화한다.

1. 크몽 이용약관, robots 정책 및 관련 안내를 다시 확인한다.
2. 필요한 경우 크몽에 개인 연구 목적의 제한적 수집 허용 여부를 문의한다.
3. 허용 범위가 불명확하면 자동 크롤링을 중단하고 수동 입력 또는 사용 허가된 데이터로 분석 기능만 검증한다.
4. 정책이나 페이지 안내가 변경되면 수집을 즉시 중지할 수 있는 Kill Switch를 제공한다.

### 4.2 저부하 수집 정책

허용 여부가 확인된 경우에도 다음 제한을 적용한다.

| 항목 | 기본값 |
|---|---:|
| 동시 요청 수 | 1 |
| 요청 간 최소 간격 | 3초 |
| 권장 실제 간격 | 3~5초 랜덤 지연 |
| 목록 정기 확인 | 30~60분 간격 |
| 상세 페이지 요청 | 신규 또는 변경 의심 항목만 |
| 타임아웃 | 15초 |
| 재시도 | 최대 2회 |
| 오류 대응 | 지수 백오프 및 일시 중단 |
| 403·429·CAPTCHA | 즉시 수집 중단, 자동 우회 금지 |

3초는 목표 속도가 아니라 최소 간격이다. 응답 상태가 나쁘거나 제한 신호가 있으면 더 느리게 동작해야 한다. 전체 페이지 재수집보다 목록에서 신규 ID를 먼저 확인하고 필요한 상세 페이지만 요청한다.

### 4.3 개인정보 최소 수집

수집 허용 대상은 프로젝트 요구사항 분석에 필요한 비식별 업무 정보로 제한한다.

**수집 대상**

- 프로젝트 ID와 공개 URL
- 제목
- 카테고리와 하위 카테고리
- 진행 방식
- 의뢰인 유형의 일반 분류
- 프로젝트 시작일과 종료 예정일
- 준비 상태
- 정부지원 여부
- 프로젝트 설명과 공개 요구사항
- 공개 기술 스택과 스킬 태그
- 예산
- 세금계산서 필요 여부
- 최초 발견일, 마지막 확인일, 게시 상태

**수집 제외 대상**

- 작성자 닉네임, 실명, 프로필 이미지, 프로필 URL
- 전화번호, 이메일, 메신저 ID, 주소
- 원문에 실수로 포함된 연락처 및 개인 식별정보
- 첨부파일과 포트폴리오
- 쿠키, 세션, 인증 토큰
- 제안자·지원자 정보
- 사용자별 활동 기록

원문 설명에 연락처나 식별정보가 포함될 가능성에 대비해 저장 전에 패턴 기반 마스킹을 수행한다. 마스킹 전 원문은 로그에 남기지 않는다.

### 4.4 데이터 보존 원칙

- DB와 대시보드는 외부에 공개하지 않는다.
- 원문 전체 보존은 분석에 꼭 필요한 최소 범위로 제한한다.
- 파싱 결과와 원문 해시를 우선 보존하고, 불필요한 HTML은 장기 보관하지 않는다.
- 관리자 접근은 본인 계정으로 제한한다.
- 로그에는 URL의 프로젝트 ID와 처리 결과만 기록하고 본문은 기록하지 않는다.
- 삭제 필요 시 프로젝트 단위로 원문과 파생 분석을 함께 제거할 수 있어야 한다.

## 5. 핵심 사용자와 사용 시나리오

### 5.1 핵심 사용자

초기 사용자는 서비스 소유자인 1인 개발자 한 명이다. 다중 사용자, 조직 권한, 공개 회원가입은 MVP에 포함하지 않는다.

### 5.2 주요 사용 시나리오

#### 시나리오 A. 시장의 최신 수요 확인

사용자는 대시보드에 접속해 최근 7일간 새로 등장한 의뢰, 급증한 기능, 예산 분포를 확인한다.

#### 시나리오 B. 반복 니즈 탐색

“관리자 페이지”, “예약”, “결제”, “알림”처럼 반복 등장하는 기능을 선택하고 관련 업종, 예산, 함께 요구되는 기능을 분석한다.

#### 시나리오 C. 1인 개발 적합 기회 찾기

낮은 운영 복잡도, 반복 수요, 표준화 가능성, 합리적 MVP 범위를 가진 의뢰군만 필터링해 제품 아이디어 후보를 검토한다.

#### 시나리오 D. 외주 대응 자산 준비

자주 등장하는 기술과 기능을 바탕으로 재사용 가능한 인증, 관리자, 결제, 알림 등의 공통 모듈 준비 우선순위를 정한다.

#### 시나리오 E. 근거 검증

AI가 제안한 “업종별 예약 관리 SaaS” 아이디어를 클릭해 근거 의뢰, 발견 빈도, 예산, 요구사항 원문을 직접 검토한다.

## 7. 수집·정제 기능 상세

### 7.1 수집 흐름

```text
스케줄 실행
→ 수집 허용·Kill Switch 확인
→ 목록 페이지 1회 요청
→ 프로젝트 ID와 목록 메타데이터 추출
→ DB의 기존 ID와 비교
→ 신규·변경 의심 상세 페이지만 순차 요청
→ 개인정보 마스킹
→ Zod 스키마 검증
→ 프로젝트와 스냅샷 저장
→ 분석 작업 큐 등록
→ 실행 결과 기록
```

### 7.2 신규·변경 판별

- 프로젝트 ID를 외부 고유키로 사용한다.
- 정규화한 분석 대상 필드로 콘텐츠 해시를 생성한다.
- 같은 ID와 같은 해시는 `lastSeenAt`만 갱신한다.
- 해시가 변경되면 새 스냅샷을 추가한다.
- 일정 기간 목록에서 발견되지 않더라도 즉시 삭제하지 않고 상태를 `unknown`으로 둔다.

### 7.3 파서 내구성

- 화면의 CSS 클래스 하나에만 의존하지 않는다.
- 레이블과 구조를 함께 이용하되, 필수 필드 누락을 감지한다.
- 금액과 날짜의 원문 값 및 정규화 값을 구분한다.
- 알 수 없는 값은 추정하지 않고 `null`과 파싱 경고로 남긴다.
- 파서 버전을 스냅샷에 기록한다.

## 8. 분석 체계

### 8.1 분석 단위

| 분석 축 | 예시 |
|---|---|
| 고객 문제 | 수작업 예약 관리, 상담 누락, 운영 데이터 분산 |
| 업종 | 교육, 병원, 커머스, 커뮤니티, 제조 |
| 제품 유형 | 웹, 앱, 관리자, 자동화, 데이터 분석 |
| 기능 | 인증, 결제, 채팅, 예약, 알림, 리포트 |
| 기술 | Flutter, React, Node.js, AWS |
| 사업 조건 | 예산, 기간, 신규 구축, 리뉴얼, 유지보수 |
| 실행 난이도 | 외부 연동, 실시간성, 앱 심사, 보안, 운영 부담 |

### 8.2 니즈 클러스터

LLM을 사용할 경우 서비스별 분석 프롬프트와 출력 Zod 스키마를 `crawlkmong-api`에 둔다. LLM은 다음 값을 제안하되 사실로 확정하지 않는다.

- 핵심 문제
- 대상 사용자 또는 업종
- 요구 기능
- 기대 결과
- 기존 업무 방식
- 반복 가능한 제품 요소
- 구축형 요구와 SaaS형 요구의 구분

분석 결과에는 모델, 프롬프트 버전, 생성 시각, 근거 프로젝트 ID를 기록한다.

### 8.3 1인 개발 적합도

각 제품 기회는 다음 항목을 1~5점으로 평가한다.

| 평가 항목 | 높은 점수의 의미 |
|---|---|
| 수요 빈도 | 유사한 문제가 반복적으로 등장함 |
| 최근 성장성 | 최근 기간에 언급이 증가함 |
| 지불 신호 | 관련 의뢰의 예산과 구체성이 충분함 |
| 표준화 가능성 | 고객별 커스텀 개발 없이 공통 제품화 가능 |
| MVP 단순성 | 핵심 가치를 작은 범위로 검증 가능 |
| 운영 적합성 | 1인이 지원·보안·장애 대응을 감당 가능 |
| 경쟁 차별화 | 기존 제품과 다른 좁고 분명한 진입점이 있음 |

단순 합산 점수만 표시하지 않고 감점 이유도 함께 제공한다. 실시간 채팅, 양면시장, 의료·금융 규제, 대규모 콘텐츠 검수처럼 운영 부담이 큰 항목은 별도 위험 배지로 표시한다.

기회: 반복 업무가 명확하고 기능 표준화 가능
위험: 문자 발송 비용, 고객별 데이터 이관 요구
권장 MVP: 상담 접수 + 일정 + 알림 + 상태 관리

## 12. 시스템 구성

```text
Next.js 반응형 웹 (crawlkmong-web)
          ↓ 순수 TypeScript API Client
Hono REST API (crawlkmong-api, Vercel)
          ↓
Use Case / Parser / Analyzer / Batch
          ↓
Supabase PostgreSQL (crawlkmong schema)

Vercel Cron 또는 수동 Trigger
          ↓
저부하 수집 Batch Use Case
```

### 12.1 모노레포 구조

```text
apps/
├─ crawlkmong-web/
└─ crawlkmong-api/

packages/
├─ api-contracts/crawlkmong/
├─ api-client-core/
├─ crawlkmong-api-client/
├─ database/
├─ auth/
├─ llm/
├─ logging/
└─ batch/

database/
├─ migrations/crawlkmong/
└─ seeds/crawlkmong/
```

### 12.2 구현 원칙

- 프론트엔드는 DB에 직접 접근하지 않는다.
- 크롤링과 분석의 핵심 로직은 `crawlkmong-api` Use Case에 둔다.
- DB Trigger나 Supabase Edge Function에 수집 정책과 분석 로직을 숨기지 않는다.
- SQL은 직접 작성하고 모든 외부 값에 Parameter Binding을 사용한다.
- 파서 입력, 외부 응답, LLM 출력은 `unknown`으로 받은 후 Zod로 검증한다.
- API Client는 React와 Next.js에 의존하지 않는 순수 TypeScript로 작성한다.
- Cron은 실행 계기일 뿐이며 수집 핵심 로직은 일반 Node.js에서도 실행 가능하게 한다.

## 13. 배치 운영 설계

### 13.1 초기 적재

초기 적재는 모든 목록 페이지를 한 번에 빠르게 순회하지 않는다.

1. 사용자가 실행을 명시적으로 시작한다.
2. 체크포인트를 페이지 단위로 저장한다.
3. 요청은 3~5초 랜덤 간격으로 하나씩 실행한다.
4. 일정 요청 수마다 휴지 시간을 둔다.
5. 중단 후 마지막 완료 페이지부터 재개한다.
6. 상세 페이지는 목록 저장 후 별도 저속 작업으로 처리한다.

### 13.2 증분 수집

- 기본 30~60분 간격으로 목록 1페이지만 확인한다.
- 마지막으로 본 프로젝트 ID를 만나면 추가 상세 조회를 멈춘다.
- 신규 프로젝트만 상세 조회한다.
- 이미 저장된 프로젝트의 변경 확인은 낮은 빈도의 별도 작업으로 수행한다.

### 13.3 장애 대응

| 상황 | 동작 |
|---|---|
| 네트워크 오류 | 최대 2회 지수 백오프 후 다음 실행으로 연기 |
| HTTP 429 | 즉시 중단하고 최소 24시간 자동 재개 금지 |
| HTTP 403 | 즉시 중단하고 수동 검토 필요 |
| CAPTCHA·로그인 요구 | 우회하지 않고 중단 |
| 파싱 필수 필드 누락 | 저장하지 않고 구조 변경 경고 |
| 개인정보 의심 | 해당 본문 격리 또는 폐기, 관리자 검토 |
| 중복 실행 | 두 번째 실행 거부 |

## 17. 테스트 전략

### 정상 테스트

- 목록에서 프로젝트 ID, 제목, 상세 URL을 추출한다.
- 상세에서 예산, 일정, 설명, 기술을 정규화한다.
- 신규 프로젝트가 한 번만 저장된다.
- 대시보드 집계와 근거 프로젝트 수가 일치한다.

### 경계 테스트

- 예산 협의, 일정 미정, 기술 미지정 값을 처리한다.
- 긴 설명과 여러 섹션을 처리한다.
- 기존 프로젝트 내용 변경 시 스냅샷을 추가한다.
- 같은 기능의 유사 표현을 무리하게 하나로 합치지 않는다.

### 실패·안전 테스트

- 전화번호와 이메일이 포함된 본문을 저장 전에 마스킹한다.
- 작성자 닉네임과 프로필 이미지를 저장하지 않는다.
- 429와 403 응답에서 수집이 중단된다.
- CAPTCHA를 우회하지 않는다.
- DOM 구조가 바뀌어 필수 필드가 사라지면 잘못 저장하지 않는다.
- 동시에 두 배치가 실행되지 않는다.
- Kill Switch가 켜진 상태에서는 네트워크 요청을 보내지 않는다.

| 페이지 구조 변경 | 파서 버전, 회귀 샘플, 필수 필드 검증 |
| 개인정보 혼입 | 수집 필드 제한, 저장 전 마스킹, 로그 본문 금지 |
| 표본 편향 | 크몽 의뢰가 전체 시장을 대표하지 않음을 명시 |
| AI의 과도한 일반화 | 근거 수와 원문 연결, 사용자 승인, 신뢰도 표시 |
| 높은 빈도만 좇는 오류 | 예산·성장성·반복성·운영 난이도를 함께 평가 |
| 대형 구축 의뢰를 SaaS 기회로 오해 | 표준화 가능성과 1인 운영 적합도 별도 평가 |
| 서버리스 실행 시간 초과 | 체크포인트 기반 작은 배치로 분할 |

## 19. 핵심 의사결정

1. 이 서비스는 공개 판매용 크몽 미러가 아니라 본인만 사용하는 비공개 리서치 도구다.
2. 사람이나 계정을 분석하지 않고 프로젝트의 비식별 업무 요구만 분석한다.
3. 자동 수집보다 정책 준수와 대상 사이트 부하 방지를 우선한다.
4. 요청은 동시 1개, 최소 3초 간격으로 제한하고 제한 신호가 있으면 중단한다.
5. AI 분석은 결론이 아니라 검토 후보이며 모든 결과에 근거 프로젝트를 연결한다.
6. 초기 제품 가치는 수집량이 아니라 실행할 만한 고객 문제를 발견하는 데서 판단한다.

## 20. 최종 산출물 정의

MVP가 완료되면 다음 결과물을 갖는다.

- 크몽 공개 IT 의뢰의 비식별 업무 데이터 저장소
- 저부하·중단 가능한 수집 파이프라인
- 프로젝트 검색과 필터 대시보드
- 니즈·기능·기술·예산 분석 화면
- 1인 개발 관점의 제품 기회 후보 목록
- 각 분석에서 원문 근거로 이동하는 추적 구조
- 사용자가 제품 후보를 채택·관찰·보류하고 메모하는 개인 연구 워크플로

이 서비스의 최종 성공은 “많이 수집했다”가 아니라 다음 질문에 매주 더 나은 답을 주는 것이다.
